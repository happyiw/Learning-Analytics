# ETL и аналитический контур

## Текущее решение

Проект использует гибридный incremental ETL:

1. API сохраняет транзакционный факт обучения (`TestAttempt`, `UserAnswer`, `LessonProgress`).
2. В той же транзакции добавляется append-only событие в `learning_events`.
3. Фоновый worker выбирает outbox-пакеты с `FOR UPDATE SKIP LOCKED` и пересчитывает затронутые
   строки `student_module_metrics` вне транзакции HTTP-запроса.
4. Read API студента и преподавателя асинхронно читает компактный read-model set-based
   SQL-запросами.
5. Команда `python -m backend.rebuild_analytics` выполняет полный batch-пересчёт для сверки.

Такой подход сохраняет транзакционную согласованность, ускоряет чтение и не требует отдельной
инфраструктуры при текущем объёме данных.

## Почему не чистый batch

Только пакетный пересчёт создаёт задержку между завершением теста и появлением рекомендации.
Для интерактивной LMS это ухудшает пользовательский сценарий. Batch остаётся полезным как:

- ночная сверка агрегатов;
- восстановление после изменения формул;
- backfill после миграции;
- переобучение будущих ML-моделей.

## Почему Kafka пока не нужна

Kafka оправдана, когда одновременно выполняются несколько условий:

- устойчивый поток в тысячи событий в секунду;
- несколько независимых потребителей событий;
- требуется replay большого журнала;
- аналитика развёрнута отдельно от transactional API;
- нужна межсервисная доставка с partitioning и consumer groups.

Текущий проект имеет один backend, одну PostgreSQL и небольшой поток событий. Kafka повысит
операционную сложность сильнее, чем производительность. PostgreSQL outbox достаточен.

## Когда переходить к streaming

Переход целесообразен при появлении realtime-дашбордов, clickstream, ML feature pipeline,
уведомлений и нескольких сервисов-потребителей. Порядок миграции:

1. Outbox publisher читает `learning_events WHERE published_at IS NULL` с `FOR UPDATE SKIP LOCKED`.
2. События публикуются в Kafka по ключу `user_id` или `course_id`.
3. После подтверждения broker заполняется `published_at`.
4. Потребитель обновляет read-model идемпотентно по `event_id`.
5. Batch reconciliation сохраняется как механизм восстановления.

Рекомендуемые топики: `learning.activity.v1`, `analytics.metric-refresh.v1` и
`recommendations.generated.v1`. Схемы следует версионировать через Avro/Protobuf и Schema Registry.

## ML-контур

ML лучше строить как пакетное обучение плюс потоковый/инкрементальный inference:

- offline features и обучение — batch;
- обновление online features — из event/outbox;
- выдача риска и рекомендаций — из versioned model service;
- rule-based engine остаётся fallback;
- качество контролируется временным test split, calibration и drift monitoring.

Команда `python -m backend.ml_features --output artifacts/ml_features.csv` формирует
воспроизводимый offline feature snapshot без искусственного target. Целевую переменную следует
добавлять только после определения реального бизнес-события (например, провал итогового контроля
или прекращение активности), иначе модель будет лишь воспроизводить текущие ручные правила.
