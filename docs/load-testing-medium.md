# Профиль Medium и результаты нагрузочного тестирования

## Состав набора

Генератор `backend.generate_load_dataset` создаёт воспроизводимый синтетический набор с
фиксированным seed, не удаляя demo-данные:

| Сущность | Количество |
|---|---:|
| Студенты | 5 000 |
| Курсы по информационной безопасности | 20 |
| Модули / уроки | 300 / 1 800 |
| Задания / тесты | 600 / 600 |
| Вопросы / варианты ответа | 2 400 / 9 600 |
| Прогресс уроков | 300 000 |
| Попытки тестов | 500 000 |
| Ответы / выбранные варианты | 2 000 000 / 2 000 000 |
| События обучения | 2 000 000 |

Большие данные записываются напрямую в PostgreSQL через `COPY`, а не хранятся в Git.
Повторная генерация выполняется с `--replace`. Диапазоны идентификаторов Medium отделены от
demo seed, поэтому удаляются только синтетические записи генератора.

```powershell
docker compose exec backend python -m backend.generate_load_dataset
docker compose exec backend python -m backend.rebuild_analytics
```

Тестовые студенты имеют имена `load_medium_00001` … `load_medium_05000` и пароль
`loadpass`. Эти учётные данные предназначены только для локального нагрузочного стенда.

## Фактический прогон

Прогон выполнен на локальном Docker-стенде. После загрузки вместе с demo seed получено 5 052
пользователя, 21 курс, 304 модуля, 1 815 уроков, 500 449 попыток и 2 004 480 ответов.
Размер PostgreSQL до смешанного теста — 1,096 ГБ.

Наиболее дорогие этапы загрузки:

- 2 млн ответов — 131,5 с;
- 2 млн связей ответ-вариант — 79,0 с;
- 2 млн событий — 134,5 с.

Время включает обновление индексов и проверку внешних ключей при commit. Пакетная
материализация 75 184 строк `student_module_metrics` заняла 3,93 с. `VACUUM ANALYZE` — 1,32 с.

## Смешанный профиль API

Сценарий `scripts/mixed_load_test.mjs` выполнил 10 000 запросов с concurrency 50 и пулом из
100 студентов:

| Операция | Доля | p50, мс | p95, мс | p99, мс | Ошибки |
|---|---:|---:|---:|---:|---:|
| Student analytics snapshot | 45% | 4 033 | 7 696 | 9 027 | 0 |
| Recommendations | 20% | 3 583 | 7 042 | 8 333 | 0 |
| Teacher dashboard | 20% | 2 087 | 3 844 | 4 622 | 0 |
| Course progress | 10% | 872 | 3 173 | 4 181 | 0 |
| Lesson completion (write) | 5% | 868 | 2 762 | 4 172 | 0 |

Общий результат: 702,98 с, 14,23 запроса/с, HTTP-ошибок нет. Backend использовал примерно
2,5–3,1 CPU и до 254 МБ RAM; PostgreSQL в наблюдаемом пике — около 1,27 CPU и 866 МБ RAM.
После записи 500 событий размер БД вырос до 1,115 ГБ.

Запуск сценария:

```powershell
node scripts/mixed_load_test.mjs
```

Параметры задаются переменными окружения `BASE_URL`, `REQUESTS`, `CONCURRENCY`,
`STUDENT_TOKENS` и `LOGIN_CONCURRENCY`.

## Выводы и следующий порог оптимизации

Целостность и устойчивость на Medium подтверждены: контейнеры не перезапускались, потерь и
5xx не было, запись работала одновременно с чтением. При этом latency пока не соответствует
production SLO: персональная аналитика и рекомендации повторно вычисляют исторические метрики
по модулям. Их следует перевести на `student_module_metrics` и set-based async-запросы.

Следующие меры по приоритету:

1. Читать student snapshot и рекомендации из read-model, исключив N+1 расчёты.
2. Ограничить время транзакции и явно настроить размер SQLAlchemy pool на каждый worker.
3. Добавить кэширование неизменяемого каталога и пагинацию тяжёлых ответов.
4. После оптимизации повторить тесты ступенями concurrency 10/25/50/100 и зафиксировать SLO.

Kafka не устранит текущую задержку чтения. Она станет полезна при нескольких независимых
потребителях и устойчивом большом event stream; критерии перехода описаны в
`docs/etl-architecture.md`.

## Результат после оптимизации

После перевода student snapshot, progress и recommendations на async read-model, переноса
материализации из request path и настройки connection pool тот же профиль из 10 000 запросов с
concurrency 50 завершился за 113,58 с: **88,04 RPS**, ошибок нет.

| Операция | p95 до, мс | p95 после, мс | Изменение |
|---|---:|---:|---:|
| Student analytics snapshot | 7 696 | 971 | −87% |
| Recommendations | 7 042 | 649 | −91% |
| Teacher dashboard | 3 844 | 1 105 | −71% |
| Course progress | 3 173 | 813 | −74% |
| Lesson completion | 2 762 | 505 | −82% |

Пропускная способность выросла примерно в 6,2 раза — с 14,23 до 88,04 RPS. После теста
необработанных событий нет, `idle in transaction` нет; PostgreSQL сохраняет 30 обычных idle
соединений в настроенных пулах двух backend worker.
